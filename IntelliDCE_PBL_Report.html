1. Old Architecture (Baseline Compiler Pipeline)

The initial system (IDCE Baseline) implemented a standard, linear compiler optimization pipeline focused exclusively on static, syntax-directed dead code removal. It converted high-level C/C++ source code into GIMPLE-style Static Single Assignment (SSA) intermediate representation via a Flex lexer and Bison LALR(1) parser. Optimization passes relied strictly on classical worklist algorithms: Sparse Conditional Constant Propagation (SCCP), basic-block unreachable elimination, and Mark-Sweep liveness analysis.

Critical Limitations of the Baseline Pipeline

  • Vulnerability Blindness & Dangerous Dead Stores (CWE-561): In standard liveness analysis, if a variable is not read downstream, its assignment is marked dead ($\bot$). Consequently, cryptographic zeroization routines (e.g., clearing passwords or keys with memset) were silently removed, leaving memory exposed to dumps.
  • Inability to Resolve Complex Loop-Carried Dead Structures: Classical algorithms evaluate basic blocks locally. Loop-carried computations that modify registers across iterations without contributing to any observable program output were retained due to conservative fixpoint assumptions.
  • Lack of Semantic Verification & Explainability: Pruning decisions were emitted as an unannotated black-box binary diff. Developers had no visibility into why statements were pruned or whether unsafe C-library primitives existed in the input.

2. Current Architecture (IntelliDCE + DRONA System)

The current architecture transforms the compiler from a purely syntactic optimizer into a security-aware, agentic compiler ecosystem. The system introduces four foundational pillars: a Graph Neural Network (GNN) classifier with a deterministic safety veto engine, an Automata-based static vulnerability scanner, a holistic Code Health scoring model, and DRONA—a local AI debugging assistant secured by a server-side Guardian policy layer.

1. Code Health Score (Module 1)

A deterministic 0–100 index rating codebase hygiene into 4 tiers (Critical to Excellent) based on dead code volume, cyclomatic complexity, and security defects.

2. Automata Vulnerability Scanner (Mod 2)

A line-by-line lexical & DFA state acceptor enforcing 10+ formal CWE rules (Command injection, buffer overflows, format strings) before compiler execution.

3. DRONA & Guardian Agent (Mod 6)

An interactive local AI assistant (Ollama) guarded by a multi-phase semantic sanitization barrier that halts prompt injections with zero LLM execution.

3. Methodology

The project combines four formal disciplines: Theory of Automata (TOA), Compiler Graph Theory, Deep Graph Representation Learning, and Defensive Agentic AI Engineering.

3.1 Automata-Theoretic Pattern Acceptance (Module 2)

Vulnerabilities are formally defined as regular languages accepted by Deterministic Finite Automata (DFA) $M = (Q, \Sigma, \delta, q_0, F)$ over the source character alphabet $\Sigma$. The scanner operates line-by-line prior to intermediate representation lowering:

  • OS Command Invocations (CWE-78): $\Sigma^* \cdot \text{"system"|"popen"|"execl"|"execve"} \cdot [\text{\textbackslash s}]^* \cdot \text{"("} \cdot \Sigma^*$ identifies unsafe shell delegation.
  • Unbounded Memory Primitives (CWE-120): Transition function recognizes unbounded copy operations (strcpy, gets, sprintf) lacking explicit destination bounds checks.
  • Double Free State Machine (CWE-415): Models pointer life-cycle: $\text{Allocated} \xrightarrow{\text{free()}} \text{Freed} \xrightarrow{\text{free()}} \text{Hazard}$. The scanner verifies that every dynamic handle is transitioned to nullptr immediately following deallocation.
  • Cross-Pass Cryptographic Invariant (CWE-561): A higher-order lattice property combining regex token classification with SSA def-use liveness: $$\text{SensitiveVar}(v) \land \text{Liveness}(v) = \bot \implies \text{Flag Critical Hazard (Dead Zeroization)}$$

3.2 Hybrid-GNN Architecture for Subgraph Classification

Rather than treating SSA instructions as flat tokens, the program is modeled as a directed graph $G = (V, E, X)$ where $V$ represents SSA statements and basic blocks, $E$ denotes control-flow and data-dependency edges, and $X \in \mathbb{R}^{|V| \times 74}$ represents a multi-modal feature matrix (64-dimensional MiniLM semantic embedding + 10 compiler structural features: loop depth, branch depth, opcode class, def-use count, pointer dereference flags).

Stage 1 (GraphSAGE):   h_v^{(1)} = \text{ReLU}\left( W_1 \cdot \text{CONCAT}\left( x_v, \frac{1}{|\mathcal{N}(v)|} \sum_{u \in \mathcal{N}(v)} x_u \right) \right) \\ Stage 2 (Multi-Head GAT):   h_v^{(2)} = \sum_{k=1}^K \sum_{u \in \mathcal{N}(v)} \alpha_{vu}^k W_2^k h_u^{(1)}, \quad \alpha_{vu} = \text{Softmax}_u\left( \text{LeakyReLU}\left( a^T [W h_v || W h_u] \right) \right)

Safety Veto Engine: Even if the GNN assigns a high probability of deadness ($p > 0.6$), the statement is guarded by an axiomatic compiler veto rule. Any statement containing volatile qualifiers, I/O side-effects, atomic operations, or unknown function calls with pointer arguments is permanently retained.

3.3 Code Health Composite Formulation (Module 1)

The overall software maintainability and safety posture is unified into a scalar index $S \in [0, 100]$:

S = 100 - \min(30, \lfloor 0.75 \times \text{DeadPct} \rfloor) - \min(35, 12 \times N_{\text{vuln}}) - \min\left(15, \left\lfloor 0.15 \times \min\left(100, 18 \times \frac{N_{\text{branches}}}{N_{\text{blocks}}}\right) \right\rfloor\right)

3.4 Defensive AI Engineering & Guardian Architecture (DRONA)

DRONA operates under strict security invariants:

  • Untrusted Model Invariant: The LLM is treated as an untrusted proposal engine. No model output is displayed or executed without deterministic validation.
  • Zero Execution Authority: DRONA possesses no shell, filesystem, or outbound network socket capabilities. Its powers are restricted to a read-only allowlist: scan_code, explain_statement, show_health.
  • Input/Output Guardian Pipeline: Every inbound user message and code comment passes through multi-layer semantic normalization: Unicode NFKC decomposition, zero-width character stripping, base64 blob decoding, leetspeak mapping, and spaced-letter consolidation.
  • Fixed-Refusal Preemption: If an input's weighted threat score exceeds the threshold ($T=60$), the server returns a fixed refusal string immediately. The LLM is never invoked, completely eliminating token expenditure and jailbreak vulnerability.

4.3 Guardian & DRONA Agent Verification (Module 6)

The DRONA subsystem was subjected to 65 automated test cases testing security boundaries, offline resilience, and model fidelity:

  • Guardian Test Suite (20/20 Passed): Successfully intercepted direct instruction overrides, multi-token combos (override + bypass + verdict manipulation score = 95), leetspeak obfuscations (1gn0r3 th3 s3cur1ty p0l1cy), spaced-letter injections (i g n o r e), base64 encoded payloads, and indirect prompt injections hidden inside code comments. Benign developer inquiries ("How do I disable this warning in my IDE?") achieved 100% false-positive rejection ($S=0$, allowed).
  • LLM Client Suite (18/18 Passed): Verified offline error handling (LLM_OFFLINE), timeout recovery (LLM_TIMEOUT), streaming NDJSON aggregation, model auto-discovery, and single-retry schema repair for malformed JSON outputs.
  • DRONA Brain Suite (27/27 Passed): Confirmed that blocked injection attempts make zero calls to the model, malicious code suggestions (e.g., introducing system()) are caught by the scanner and withheld, unauthorized tools are rejected, and session memory strictly retains a 6-turn sliding window.
  • Live Execution Performance: In live inference on local hardware using Ollama (qwen2.5-coder:7b), DRONA demonstrated end-to-end response latency of 2.8s to 6.3s with zero cloud dependencies.
